## 4. 사례 A — 몸통 파괴 시 머리 당김 (메인)

### 상황
- 분절형 뱀 적: 머리 + 몸통 N칸, `PathRoute` 위 거리 기반 이동.
- 몸통이 파괴되면 **앞쪽이 한 칸 당겨지는** 연출이 필요 (과제·게임feel).

### AI / 초안 쪽 (예시 — 본인 대화에 맞게 수정)
- [ ] “파괴된 세그먼트 Transform만 제거하면 된다”
- [ ] “머리 `transform.position`을 수동으로 뒤로 옮긴다”

### 내가 본 문제 (검증 기준)
- 위치만 옮기면 **경로 위 진행 상태(`headDistance`)와 시각이 어긋남**.
- 남은 세그먼트는 모두 `headDistance - 뒤처짐거리`로 좌표를 구함 → **진행 거리 값을 줄이는 쪽**이 규칙과 일치.
- 같은 프레임에 전체 재배치 필요 (`RefreshSegmentPositions`).

### 최종 결정 (코드)
- `OnSegmentDestroyed`에서 리스트에서 제거 후  
  `headDistance = Mathf.Max(0f, headDistance - segmentSpacing)`  
  → 즉시 `RefreshSegmentPositions()`.
- 파일: `SnakeEnemy.cs` (대략 `OnSegmentDestroyed` 구간).

### 한 줄 (과제용)
> AI가 제안한 “위치 보정” 대신, **경로 진행 거리(`headDistance`) 보정**으로 통일해 세그먼트 추종 규칙이 깨지지 않게 했다. 검증은 Unity 좌표 재현과 “몸통 N개 제거 후 머리가 한 칸 뒤로 당겨지는지” 플레이로 확인했다.

### 첨부하면 좋은 것
- [ ] `SnakeEnemy.cs` 해당 메서드 스크린샷
- [ ] 플레이 영상에서 몸통 파괴 직후 머리 당김 구간 (캡처 1장)
- [ ] (선택) Cursor 대화 일부 — “위치 vs 거리” 질문·답

## 5. 사례 B — PathRoute 구간 길이 캐싱 (서브, 짧게)

### 상황
- `GetPointAtDistance`가 **매 프레임 × (세그먼트 + 몸통 디스크)** 호출됨.
- 웨이포인트 **개수**는 적어도 **호출 횟수**는 많음.

### AI / 초안 (예시)
- [ ] “웨이포인트 수가 적으니 매번 `Vector3.Distance` 해도 된다”

### 검증 기준 (프로파일 없이)
- 플레이 중 구간 **길이**는 불변 → `segmentLengths[]`, `totalLength` 한 번 계산.
- **좌표**는 `waypoints[i].position`에서 계속 읽음 (길이만 캐시).
- 에디터에서 웨이포인트 변경 시 → `OnValidate`에서 `cacheBuilt = false`.

### 최종 (코드)
- `PathRoute.BuildCacheIfNeeded()`, `Awake` / `GetPointAtDistance` / `TotalLength`에서 lazy build.
- 파일: `PathRoute.cs`

### 한 줄 (과제용)
> AI의 “매번 거리 계산” 제안을, **호출 빈도·데이터 불변성** 기준으로 검토해 구간 길이만 캐시하는 설계로 확정했다. 프로파일링 없이 호출 구조로 판단했다.

### 사례 1 — 몸통 파괴 시 머리가 뒤로 당겨지는 처리 (설계·게임 로직)

**문제로 본 것**  
과제 요구는 “몸통이 깨지면 머리가 몸 쪽으로 당겨진다”였습니다. 처음에는 파괴된 오브젝트만 지우면 될 것 같았고, AI도 비슷하게 **위치만 조금 뒤로 옮기거나** 세그먼트만 리스트에서 빼는 쪽 초안이 나왔습니다. 플레이해 보니 한 프레임은 맞는데, 이후 프레임에서 머리·몸통 간격이 어색하게 벌어지거나 규칙이 들쭉날쭉해졌습니다.

**검증 기준**  
이 프로젝트에서는 머리가 `headDistance`만 매 프레임 올리고, 나머지 몸통은 **인덱스마다 정해진 뒤처짐 거리**로 `headDistance - gap` 위치를 `PathRoute`에서 가져옵니다. 그래서 “한 번만 Transform을 옮긴다”로는 **다음 Update에서 같은 규칙으로 다시 계산되며** 당김 연출이 유지되지 않습니다. 몸통 개수가 늘어나도 **진행 거리 하나로 전체가 따라오는 구조**를 지키는 게 중요하다고 봤습니다.

**수정·확정**  
AI 제안 중 위치만 보정하는 부분은 버리고, `OnSegmentDestroyed`에서 세그먼트를 제거한 뒤  
`headDistance = Max(0, headDistance - segmentSpacing)` 로 **경로상 진행 거리 자체를 한 칸 줄인 다음**, 같은 프레임에 `RefreshSegmentPositions()`로 전체 좌표를 다시 맞췄습니다. (`SnakeEnemy.cs`)  
확인은 에디터에서 몸통을 연속으로 깨며 **머리가 한 칸씩 뒤로 당겨지는지** 플레이로 했고, 코드 주석에도 “진행 거리 줄이는 것”으로 남겨 두었습니다.

**책임**  
“당겨 보이게만”이 아니라 **이동 규칙과 같은 변수(`headDistance`)로 맞출지**는 제가 정했고, AI는 구현 초안·문장 정리에 썼습니다.

### 사례 2 — 경로 구간 길이 캐싱 (구조·확장성)

**문제로 본 것**  
`GetPointAtDistance`는 뱀 머리·몸통·몸통 위 시각 디스크까지 **매 프레임 여러 번** 호출됩니다. 웨이포인트 개수는 적어도, 나중에 몸통·디스크가 늘면 **호출 횟수만** 크게 늘어납니다. AI에게 “매번 구간 길이를 Distance로 구해도 되나”고 물었을 때, 웨이포인트가 적으면 괜찮다는 식의 답이 왔습니다.

**검증 기준**  
플레이 중에는 웨이포인트 **위치**는 바뀔 수 있지만(플레이어 목표까지 Lerp 등), 구간 **길이 배열**은 스테이지가 고정이면 한 번 잡아 두는 편이 낫다고 판단했습니다. 반면 좌표는 계속 `waypoints[i].position`에서 읽어야 해서, **길이만 캐시하고 좌표는 실시간**으로 나눴습니다. 에디터에서 웨이포인트를 옮기면 캐시가 깨지므로 `OnValidate`에서 `cacheBuilt = false`로 다시 빌드하게 했습니다. (`PathRoute.cs`)

**책임**  
프로파일 숫자는 보지 않았고, **호출 구조·데이터가 플레이 중 바뀌는지**로 채택·보완했습니다.

---

### 정리 (핵심 질문에 대한 답)

AI가 제안한 설계·코드를 **「이 프로젝트의 이동 규칙과 맞는가」「몸통·디스크가 늘어도 같은 규칙으로 유지되는가」「플레이로 재현되는가」** 로 검증했습니다. 맞지 않으면 위치 보정·매번 거리 계산 같은 안은 버리거나 줄였고, 최종 구조(`headDistance` 보정, 구간 길이 캐시)는 제가 코드에 반영한 뒤 플레이로 확인했습니다.  
완성도보다 **코어 루프가 한 사이클 도는 것**을 우선한 작은 프로젝트이지만, 위 두 지점은 “AI 초안 → 본인 기준으로 걸러서 확정”한 부분입니다.
